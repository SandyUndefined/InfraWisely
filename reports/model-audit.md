# InfraWisely Model Audit

Audit date: 2026-05-06

## Executive Summary

InfraWisely has a complete prototype AI/ML data pipeline for a hackathon demo, but it is not yet a production-ready ML system. The root repository contains two saved Random Forest demand models, several deterministic scoring/recommendation engines, processed CSV outputs, and static dashboard JSON files.

The biggest issue is consistency: `data/dashboard/summary_metrics.json` and `data/dashboard/model_explainability_summary.json` report the v2 expanded model metrics, but the main root dashboard demand/stress/scheduling artifacts still use the v1 `model_predicted_ev_load_kw` pipeline. Example: `data/dashboard/demand_forecast.json` uses `model_predicted_ev_load_kw`, while v2 predictions are saved separately in `data/processed/final_hourly_demand_with_predictions.csv` as `final_model_predicted_ev_load_kw`.

The second major issue is evaluation validity. Both demand models are trained and tested on synthetic labels generated by the same scripts, with random row-level train/test splits. Metrics are useful for checking whether the model learned the synthetic formula, but they do not prove real-world BESCOM demand forecasting accuracy.

## 7. Model-by-Model Audit

### Model 1: EV Demand Model v1

Artifact:

- `models/ev_demand_model.pkl`
- `models/ev_demand_model_metrics.json`

Training code:

- `src/models/step5_train_ev_demand_model.py`

What it predicts:

- Hourly EV charging load in kW for a zone-hour.

Input features:

- `hour`
- `time_period`
- `is_peak_hour`
- `zone_type`
- `ev_count_estimate`
- `traffic_score`
- `existing_chargers`
- `demand_growth_rate`
- `transformer_capacity_kw`
- `base_grid_load_kw`

Target variable:

- `predicted_ev_load_kw`

Train/test split:

- Random row-level 80/20 split with `random_state=42`.
- Metrics file reports 480 rows, 384 train rows, 96 test rows.

Metrics:

- MAE: 56.6194 kW
- RMSE: 69.1330 kW
- R2: 0.851304
- Baseline MAE: 146.5136 kW
- Baseline RMSE: 179.3555 kW

Possible data leakage:

- No direct leakage from excluded columns such as `total_load_kw`, `load_ratio_after_ev`, and `risk_level`.
- The main leakage risk is evaluation design: the same 20 zones and same 24-hour profile structure are randomly mixed across train and test. This means the test set contains near-neighbor rows from the same synthetic zone profiles.
- The target is itself generated from the same features using Step 4 synthetic rules. The model is learning the generator, not measured demand.
- `time_period` and `is_peak_hour` duplicate information already present in `hour`. This is not leakage, but it inflates apparent feature signal.

Whether preprocessing is correct:

- Mostly correct for a tabular sklearn prototype.
- Uses `ColumnTransformer` with `OneHotEncoder(handle_unknown="ignore", sparse_output=False)` for categorical columns.
- Numeric columns pass through directly.
- Booleans are cast before training.
- Missing: no imputation, no schema/version validation at inference, and no dependency pinning.

Whether the metric is correct:

- MAE/RMSE/R2 are appropriate regression metrics for EV load kW.
- The baseline comparison to train-mean prediction is useful but weak.
- The metrics are not sufficient evidence of real forecasting performance because labels are synthetic and the split is random row-level.

What is missing:

- Real charger session/load data target.
- Time-based split or zone-holdout split.
- Feature contract for inference.
- Model card explaining synthetic data limitations.
- Reproducible environment file.
- Tests verifying `models/ev_demand_model.pkl` can be loaded and predicts from the documented schema.

### Model 2: EV Demand Model v2 Expanded Synthetic

Artifact:

- `models/ev_demand_model_v2.pkl`
- `models/ev_demand_model_v2_metrics.json`

Training code:

- `scripts/retrain_final_model_with_expanded_data.py`

What it predicts:

- Synthetic hourly EV charging load in kW across simulated days, weather, weekday/weekend, and hourly traffic conditions.

Input features:

- `hour`
- `time_period`
- `is_peak_hour`
- `zone_type`
- `day_type`
- `is_weekend`
- `weather_condition`
- `temperature_c`
- `ev_count_estimate`
- `traffic_score`
- `traffic_score_hourly`
- `existing_chargers`
- `charger_utilization_proxy`
- `demand_growth_rate`
- `transformer_capacity_kw`
- `base_grid_load_kw`

Target variable:

- `synthetic_ev_load_kw`

Train/test split:

- Random row-level 80/20 split with `random_state=42`.
- Metrics file reports 28,800 rows, 23,040 train rows, 5,760 test rows.

Metrics:

- MAE: 51.3838 kW
- RMSE: 68.6991 kW
- R2: 0.916586
- Baseline MAE: 191.2440 kW
- Baseline RMSE: 237.9215 kW

Possible data leakage:

- No direct target column leakage from `synthetic_total_load_kw`, `synthetic_load_ratio`, or `synthetic_risk_level`; these are not listed as features.
- Strong synthetic-generator leakage exists because `synthetic_ev_load_kw` is generated from the same engineered factors that become features.
- Random row split mixes the same zones, day patterns, and hourly profiles across train and test. A stronger validation would hold out future days or entire zones.
- `day_index` is not a feature even though `day_growth_factor` affects the target. That means the model cannot represent growth over the simulated 60 days except indirectly through random mixing.
- `traffic_score_hourly` and `charger_utilization_proxy` are valid only if they are available or forecastable at inference time. Otherwise they become unrealistic future-known inputs.

Whether preprocessing is correct:

- Mostly correct for a sklearn prototype.
- Uses one-hot encoding for categorical features and passes numeric features through.
- Missing imputation and input validation.
- The model artifact is very large at 509 MB for a hackathon MVP, which may be awkward for Git, deployment, and API cold starts.

Whether the metric is correct:

- MAE/RMSE/R2 are correct regression metrics.
- The reported R2 is higher than v1, but the validation is still synthetic and row-random.
- The metric currently measures fit to a simulation, not BESCOM operational accuracy.

What is missing:

- Clear decision on whether v2 is the canonical model.
- Regeneration of all dashboard/stress/schedule outputs from v2 predictions.
- Fixed script paths so v2 retraining runs from this repo root.
- Deployment-size strategy for the 509 MB pickle.
- Real validation dataset or at least holdout-by-day/holdout-by-zone evaluation.

## 8. Cross-Cutting Issues

1. Canonical model ambiguity

The teammate handoff says v2 is final, and dashboard summary/explainability show v2 metrics. However, root dashboard demand/stress/scheduling files are still based on v1 predictions. Pick one canonical model and regenerate all downstream outputs from it.

2. Synthetic data limitation

The pipeline is internally coherent, but most labels and grid constraints are generated. The MVP should say "prototype using synthetic/masked grid and demand data" rather than implying measured demand.

3. Script path bug in final scripts

`scripts/retrain_final_model_with_expanded_data.py`, `scripts/build_final_ai_ml_prototype.py`, and `scripts/build_final_dashboard_data.py` use `Path(__file__).resolve().parents[2]`, which points outside this repo. In this repository layout it should likely be `parents[1]`.

4. Missing dependency management

The code imports `pandas`, `numpy`, `scikit-learn`, `joblib`, `requests`, and `pdfplumber`, but no dependency file is present. The checked-in `.myenv` does not contain the required packages.

5. Missing backend and incomplete frontend shell

The backend is only described in `TEAMMATE_NEXT_STEPS.md`. The frontend has JS logic but no HTML/CSS/package files in this repo.

6. No automated tests

There are no tests for data schema, model loading, prediction shape, JSON exports, or pipeline reproducibility.

## 9. Recommended Next Fixes

Priority order:

1. Decide whether v1 or v2 is the canonical demo model.
2. If v2 is canonical, regenerate `demand_forecast.json`, `grid_stress_alerts.json`, `scheduling_recommendations.json`, `load_curve_before_after.json`, `station_recommendations.json`, and `map_zones.json` from v2 outputs.
3. Fix `Path(...).parents[2]` to the correct repo root in final scripts.
4. Add `requirements.txt` or `pyproject.toml`.
5. Add a small validation script that loads the canonical model, checks feature schema, predicts one sample row, and verifies dashboard JSON consistency.
6. Add explicit wording in the dashboard/report that demand and grid capacity are synthetic/masked for the hackathon MVP.
7. Add a basic backend or restore the missing static frontend shell so the dashboard is runnable from this repository.
